# 麦麦图鉴 · 设计文档

> 版本 v2.0 · 2026-10-20 · 配合《麦麦图鉴-项目方案》食用
>
> v2 变更：稀有度梯度重构、图鉴池只收单品、新增图鉴格子墙与零 Token 离线 Demo。

## 一、总体架构

```
用户对话
   ↓
WorkBuddy Skill（SKILL.md 编排：意图识别 / 工具调度 / 播报）
   ↓
麦当劳 MCP Server（mcd-mcp 连接器，真实调用）
   ↓  响应保存为本地快照 data/snapshots/*.json
收录引擎 scripts/codex.py（纯 Python 标准库 CLI）
   ↓
图鉴状态 data/codex.json + 图鉴池 data/catalog.json（本地持久化）
   ↓
渲染层 scripts/render.py
   ├── 图鉴格子墙  output/codex-wall.html   ← 主视觉
   ├── 分享卡      output/share-card.html
   └── Markdown    output/codex.md
```

选择「MCP 快照 + CLI 引擎」而非让 Skill 直接在对话里做数据处理的理由：
收录算法可独立测试、可离线复现（examples/ 脱敏数据即回归测试）、
Skill 层只负责编排与播报，职责单一。

`scripts/demo.py` 是这套引擎的离线入口：不吃 Token、不联网，直接用
`examples/` 的快照跑完整链路，30 秒内产出三种交付物。

## 二、模块划分

| 模块 | 职责 |
|---|---|
| `scripts/rarity.py` | 名称归一化、同义词表、稀有度判定（R/SR/SSR/UR） |
| `scripts/catalog.py` | 图鉴池（多时段菜单合集）构建、单品过滤、册别归类（六册） |
| `scripts/codex.py` | 订单收录（双通道）、状态持久化、等级/徽章统计、CLI |
| `scripts/render.py` | 格子墙 / 分享卡 / Markdown 三态渲染 |
| `scripts/demo.py` | 零 Token 离线演示 |

## 三、核心算法

### 3.1 在售匹配（三通道，防误判绝版）

真实数据勘察发现订单侧与菜单侧的 productCode 是两套体系
（「板烧鸡腿堡」订单 901406 / 菜单 1406），因此在售判定按顺序执行：

1. **code 精确匹配**：订单子项 code ∈ 菜单池
2. **名称归一化匹配**：去符号/空格/规格后缀（大杯、中杯…）+ 同义词表
   （可口可乐→可乐、中薯条→薯条、香芋派→派…）
3. **名称弱匹配**：归一化后互为子串且核心词 ≥3 字
   （「麦乐鸡5块」→「麦乐鸡」）

三通道全部未命中 → UR 绝版候选。

### 3.2 图鉴条目身份（防同品分裂）

「可口可乐大杯/中杯/可乐中杯」三个 code 指向同款产品。图鉴条目 key：

- 菜单池匹配成功 → 菜单 code（所有规格的薯条合并为「薯条」）
- 匹配失败 → `"n:" + 归一化名称`（两个不同 code 的香芋派合并）

### 3.3 稀有度判定（v2）

稀有度的全部意义是「越稀有越少」。v1 把「仅早餐时段供应」判成 SSR，
让早餐册 55 款 100% 变成限定款、SSR 占全池 55%，梯度彻底失效。
v2 改按**限定属性**分层，时段只做展示：

```
UR  三通道均未命中菜单池（绝版）—— 池内永远不会出现 UR
SSR 名称含联名/主题限定词（高达/世界波/泷/联名/限定/节日/周年…）
    或菜单 tags 含 上新/新品/限定/限量/联名/人气回归（促销标签除外）
SR  招牌经典款（SIGNATURE_NAMES 精确名单）
    或菜单 tags 含 人气/爆款/粉丝之选
R   其余
```

两条关键取舍：

1. **精确名单而不是子串**。「薯条」是招牌款，但「脆脆薯条」「薯条毛绒周边」不是；
   用子串匹配会把 SR 顶到 30%+。
2. **「限定特惠」是打折**。促销标签进 `PROMO_TAGS` 白名单排除，
   否则常年供应的麦咖啡会因为打折被标成限定款。

实测分布（76 款单品）：R 48 (63%) / SR 20 (26%) / SSR 8 (11%)，
`TestRarityBalance` 对「R > SR > SSR」「SSR ≤ 18%」做硬断言。

### 3.4 图鉴池口径：只收单品（v2）

图鉴的收录原子单位是**订单子项**（组合餐展开到单品），池子必须同口径，否则：

- 同一个汉堡既算「单品」又算「套餐」，一格餐品占两格；
- 148 个菜单编码里有 68 款套餐，分母虚高，进度永远上不去；
- 早餐册被「二件套 / 三件套」塞满，册别权重失衡。

因此 `catalog.combo_of()` 在采样阶段直接跳过套餐（名称/标签/分类三重判定），
`is_merch()` 跳过周边玩具，无名条目（只有编码没有名称）也跳过，
最后 `_merge_duplicate_names()` 把同名多编码（「派」「脆薯饼」）合并成一格。
CLI 会把跳过的数量报在 `skipped_combos / skipped_merch / skipped_unknown`。

### 3.5 多门店 × 双时段菜单池

`query-meals` 按餐段返回；早餐品仅在早餐时段菜单出现。
图鉴池对同一门店采样两次：

- 常规时段：不传 `reservationDate`
- 早餐时段：先用 `now-time-info` 取得北京时间，计算下一天日期，再传
  `reservationDate = "yyyy-MM-dd 10:00"`；不得传入中文相对日期。

合并后 periods 记录每个品出现的时段集合。
**UR 复活机制**：每次菜单池更新后全量重判，UR 可能自动回到在售。

**为什么要多门店并集**（v2 实测教训）：单门店采样会把「本店没上、别家门店在卖」
的餐品误判成绝版。示例数据里「培根蔬萃双层牛堡」在门店 1440001 的菜单中缺席，
被判 UR；补入门店 1440040 的菜单后它重新出现在在售，自动复活为常规款。
因此 UR 的语义应表述为「当前所有**已采样**门店的菜单里都没有」，
并且采样门店越多，UR 越可信。

### 3.6 册别归类（六册）

菜单分类名规则优先（早餐类分类 → 早餐册…），
名称关键词规则兜底（冰淇淋/麦旋风/新地/派 → 甜品册…），
联名关键词（高达/世界波/泷）→ 限定册。

### 3.7 视觉层：把「图鉴」画出来（v2）

v1 的交付物只有数字 + 进度条，看不到任何一格餐品——「把一个视觉产品交付成了数据报表」。
v2 的视觉决策：

| 决策 | 理由 |
|---|---|
| 一格一餐品，网格铺满 | 图鉴的灵魂是「点格子」，不是「看报表」 |
| 未点亮格用**同一张官方图做剪影** | 「看得见轮廓、猜不到是谁」才是收集欲的来源 |
| 剪影用 `mix-blend-mode: multiply` | 产品图是白底 PNG，压黑会得到一整块黑砖；multiply 让白底融进纸色，只留产品轮廓 |
| 稀有度 = 边框色 + 角标 | R 墨灰 / SR 蓝 / SSR 金 / UR 全息描边，一眼可辨 |
| UR 单独「绝版殿堂」 | 最重的炫耀资本要有专属舞台 |
| 顶部 conic-gradient 完成度环 | 进度是收集玩法的仪式感 |
| 单文件自包含 HTML（无外部 JS/CSS） | 双击即看、可直接截图、可离线交付 |
| `<img onerror>` + 底层占位符 | 断网/坏链时也不会出现破图 |

分享卡同样改造：从「6 个数字格」变成「我集到的这几格」（按 UR→SSR→SR 取 6 格带图缩略）
+ 「最珍贵的收藏」特写。晒图的人终于能说清「我集到了什么」。

## 四、状态文件

### codex.json（个人图鉴状态，gitignore）

```json
{
  "schema_version": 1,
  "items": {
    "4810": {
      "name": "薯条", "book": "小食册", "rarity": "SR",
      "first_unlock": "2026-08-25 18:17:45",
      "store": "麦当劳珠海唐家福乐购百货餐厅",
      "count": 13, "image": "https://menu-img.mcd.cn/...",
      "catalog_code": "4810", "product_code": "4810"
    }
  },
  "stores": {"1440040": {"name": "...", "visits": 2}},
  "orders_seen": ["..."]
}
```

- `orders_seen` 防重复补录（order-list 每 10 单滚动）
- key 即 3.2 的归一化身份
- `product_code` 是订单侧编码，池外餐品（UR）靠它回查官方图

### catalog.json（图鉴池，可由快照重建）

products（code → name/image/tags/book/periods/rarity）+ sources（采样来源）。

## 六、已知约束与对策

| 约束 | 对策 |
|---|---|
| order-list 仅 10 单、无分页 | 增量补录定位；主机制走主动收录 |
| 菜单按餐段返回 | 双时段采样；区域限定品「发现即补录」 |
| 菜单里近一半是套餐/周边 | 采样阶段过滤，池内只留单品（3.4） |
| realTotalAmount 可能为 "0" | 不作消费凭证，只看餐品 |
| 用户绕过 Skill 下单 | 打开图鉴即自动补录兜底 |
| UR 误判风险（池不完整） | 三通道保守匹配 + 复活机制自动修正 |
| UR 已下架、没有菜单图 | 按商品编码回查图 CDN + HEAD 校验（`--probe-images`） |
| 断网/坏链导致破图 | `<img onerror>` 移除 + 底层占位符 |

## 七、验证记录（2026-10-20，真实 MCP 数据 · v2 重跑）

- 图鉴池：两家门店（1440001 / 1440040）× 双时段采样，**208 个菜单编码** →
  剔除 99 款套餐、2 款周边、1 款无名条目，同名合并后 **93 款单品入册**
  （汉堡 15 / 早餐 22 / 小食 18 / 甜品 9 / 饮品 27 / 限定 2）
- 稀有度分布：R 56 (60%) / SR 21 (23%) / SSR 16 (17%)，梯度单调
  （16 款 SSR 全部是当季新品与联名款：龙焰系列、蘸酱炸鸡、北非蛋麦满分、高达/泷）
- 补录 10 单（9 完成 1 取消）：点亮 13 款，取消单正确跳过
- 同品合并验证：「薯条」×13（三个订单 code 合并）、「可乐」×6、「麦乐鸡」×5
- 绝版检测：「泰式炭烤风味猪猪堡」判 UR，并经 `--probe-images` 回查到官方图（MS_521879）
- **UR 复活实证**：「培根蔬萃双层牛堡」单门店采样时被判 UR，补入第二家门店菜单后
  发现仍在售 → 自动复活为常规款
- 早餐品（图林根香肠早安营养卷、脆香油条）不再被误判 SSR
- 脱敏示例：`examples/`（orderId 已替换，含两家门店菜单，可离线复现全链路）
- 测试：113 个全绿（`python -m unittest discover -s tests`）
